# Лабораторная работа №1 (SRE): Сервис заметок («Note Service»)
## Реализация принципов 12-Factor App, Clean Architecture и оптимизация ресурсов

---

## 1. Введение и назначение проекта

«Note Service» — это микросервисное веб-приложение для управления персональными заметками и категориями, разработанное в строгом соответствии с методологией **The Twelve-Factor App**, принципами предметно-ориентированного проектирования (**DDD / Clean Architecture**) и жесткими нефункциональными требованиями по утилизации ресурсов (SRE-фокус: потребление ОЗУ < 50 МБ, размер образов < 30 МБ).

Приложение состоит из:
1. **Backend API (Go 1.24)**: легковесный HTTP-сервис без сторонних ORM и веб-фреймворков, реализующий контракт OpenAPI 3.0 со строгой типизацией.
2. **Database (PostgreSQL 16 Alpine)**: реляционное хранилище с внешними ключами и составными индексами.
3. **Migrator (Go 1.24)**: изолированный разовый процесс принудительного наката миграций схемы БД (Factor XII).
4. **Frontend SPA (React 19 + TypeScript + Vite + Tailwind CSS v4)**: современный пользовательский интерфейс в визуальном стиле **Liquid Glass** («жидкое стекло», visionOS-подобные полупрозрачные акриловые панели с преломлением света и динамическим градиентным фоном) с фирменным маскотом — **Подсолнухом Санни (Sunny 🌻)**, теплой солнечной палитрой (желтый/янтарный) и поддержкой темной/светлой тем.

## 2. Описание предметной области (Domain Model)

Предметная область приложения организована вокруг концепции организации мыслей, заметок и категоризации.

```
       1 ┌──────────────┐
  ┌──────┤   Category   │
  │      └──────────────┘
  │ 0..*
  ▼
┌───────────────────────┐
│         Note          │
└───────────────────────┘
```

### Основные сущности:
1. **`Category` (Категория)**:
   - `ID` (`UUID v4`): глобально уникальный идентификатор.
   - `Title` (`string`): наименование категории (уникальное, без лишних пробелов, непустое).
   - `Color` (`string`): HEX-код цвета для визуализации плашек и бейджей в интерфейсе (`^#[0-9A-Fa-f]{6}$`).
   - `CreatedAt` (`time.Time`): временная метка создания категории.

2. **`Note` (Заметка)**:
   - `ID` (`UUID v4`): глобально уникальный идентификатор.
   - `Title` (`string`): заголовок заметки (непустой, валидированный).
   - `Content` (`string`): текстовое тело заметки с поддержкой Markdown разметки.
   - `IsPinned` (`bool`): флаг закрепления («Pin to top»), поднимающий заметку в начало выборки.
   - `CategoryID` (`*UUID`): опциональная ссылка на родительскую категорию (может быть `NULL`).
   - `CreatedAt` (`time.Time`): дата создания.
   - `UpdatedAt` (`time.Time`): дата последней модификации.

### Ключевые бизнес-правила (Invariants):
- **Связь при удалении**: при удалении категории ассоциированные с ней заметки не уничтожаются, а переходят в категорию «Без категории» (`ON DELETE SET NULL`), что предотвращает случайную потерю данных.
- **Приоритет закрепления**: закрепленные заметки (`is_pinned = true`) гарантированно выводятся выше остальных, сортируясь внутри групп по дате последнего обновления (`ORDER BY is_pinned DESC, updated_at DESC`).
- **Транзакционность изменений**: обновление заметок и категорий защищено единым контекстным транзактором (`Transactor`), гарантирующим согласованность данных в конкурентной среде.

## 3. Схема базы данных (DDL) и индексы

Схема базы данных развернута в PostgreSQL посредством версионированных миграций (`migrations/000001_init_schema.up.sql`):

```sql
-- Включение расширения для генерации UUIDv4
CREATE EXTENSION IF NOT EXISTS "uuid-ossp";

-- Таблица категорий
CREATE TABLE IF NOT EXISTS categories (
    id         UUID PRIMARY KEY DEFAULT uuid_generate_v4(),
    title      VARCHAR(100) NOT NULL UNIQUE,
    color      VARCHAR(7) NOT NULL CHECK (color ~* '^#[0-9A-Fa-f]{6}$'),
    created_at TIMESTAMP WITH TIME ZONE NOT NULL DEFAULT NOW()
);

-- Таблица заметок
CREATE TABLE IF NOT EXISTS notes (
    id          UUID PRIMARY KEY DEFAULT uuid_generate_v4(),
    title       VARCHAR(255) NOT NULL,
    content     TEXT NOT NULL DEFAULT '',
    is_pinned   BOOLEAN NOT NULL DEFAULT FALSE,
    category_id UUID REFERENCES categories(id) ON DELETE SET NULL,
    created_at  TIMESTAMP WITH TIME ZONE NOT NULL DEFAULT NOW(),
    updated_at  TIMESTAMP WITH TIME ZONE NOT NULL DEFAULT NOW()
);

-- Составные индексы для быстродействия запросов (< 5 мс)
CREATE INDEX IF NOT EXISTS idx_notes_pinned_updated 
    ON notes (is_pinned DESC, updated_at DESC);

CREATE INDEX IF NOT EXISTS idx_notes_category_pinned_updated 
    ON notes (category_id, is_pinned DESC, updated_at DESC);

CREATE INDEX IF NOT EXISTS idx_categories_title 
    ON categories (title);
```

```
┌────────────────────────────────────────────────────────┐
│                   Presentation Layer                   │

                            │ HTTP / REST (OpenAPI 3.0)
┌───────────────────────────▼────────────────────────────┐

└───────────────────────────┬────────────────────────────┘
                            │
┌───────────────────────────▼────────────────────────────┐
│                   Application Layer                    │
│    CategoryService, NoteService, Context Transactor    │
└───────────────────────────┬────────────────────────────┘
                            │
┌───────────────────────────▼────────────────────────────┐
│                     Domain Layer                       │
│    Pure Entities: Category, Note, Domain Errors        │
└───────────────────────────▲────────────────────────────┘
                            │
┌───────────────────────────┴────────────────────────────┐
│              Infrastructure Persistence                │
│       pgxpool.Pool (pgx/v5) + Raw Optimized SQL        │
└───────────────────────────┬────────────────────────────┘
                            │ TCP / Wire Protocol
┌───────────────────────────▼────────────────────────────┐
│                 PostgreSQL 16 Alpine                   │
└────────────────────────────────────────────────────────┘
```

- **Backend**: Go 1.24, стандартный роутер `net/http` (без тяжелых Gin/Fiber), драйвер `jackc/pgx/v5` и пул `pgxpool`, строгая кодогенерация через `oapi-codegen`, структурированное логирование `log/slog`, конфигуратор `spf13/viper`.
- **Frontend**: React 19, TypeScript, Vite, Tailwind CSS v4, Lucide Icons, Marked (рендеринг Markdown).
- **Дизайн UI**: стиль **Liquid Glass** — полупрозрачные акриловые панели с размытием фона (`backdrop-filter: blur(28px) saturate(210%)`), зеркальными фасками (`specular highlights`), интерактивным курсорным освещением и живым фоном с плавающими лепестками подсолнуха.
- **Инфраструктура**: Multi-stage Docker-образы (`alpine:3.20` и `nginx:alpine-slim`), Docker Compose, автоматизированный `Makefile`.

## 5. Аргументация соответствия 12 Факторам (The Twelve-Factor App)

### I. Кодовая база (Codebase)
> *Одна кодовая база, отслеживаемая в системе контроля версий, множество развертываний.*
- **Реализация:** Проект содержится в едином монорепозитории (`/home/pavel/projects/sre`). Из этой кодовой базы собираются артефакты для локальной разработки, тестовых сред и продакшн-образов без дублирования кода.

### II. Зависимости (Dependencies)
> *Явно объявляйте и изолируйте зависимости.*
- **Реализация:** Зависимости бэкенда строго зафиксированы в `go.mod` и верифицируются через контрольные суммы в `go.sum`. Фронтенд изолирует зависимости через `package.json` и `package-lock.json`. Системные зависимости отсутствуют — всё упаковано в минимальные Docker-контейнеры. Никаких предположений о наличии установленных утилит на хосте нет.

### III. Конфигурация (Config)
> *Сохраняйте конфигурацию в среде выполнения.*
- **Реализация:** Конфигурация сервиса (`HTTP_PORT`, `DATABASE_URL`, `LOG_LEVEL`, `LOG_FORMAT`, `SHUTDOWN_TIMEOUT`) считывается исключительно из переменных окружения (пакет `internal/infrastructure/config` на базе `viper`). В коде отсутствуют захардкоженные пароли, адреса или токены. Для быстрого развертывания предоставлен `.env.example`.

### IV. Сторонние службы (Backing Services)
> *Считайте сторонние службы подключаемыми ресурсами.*
- **Реализация:** База данных PostgreSQL трактуется как подключаемый ресурс через сетевой URI (`postgres://user:pass@host:5432/db`). Локальная база данных в Docker Compose и удаленная托管 СУБД (например, Amazon RDS / Cloud SQL) взаимозаменяемы простой сменой переменной `DATABASE_URL` без изменения и перекомпиляции кода.

### V. Сборка, релиз, выполнение (Build, Release, Run)
> *Строго разделяйте стадии сборки и выполнения.*
- **Реализация:** Реализована строгая многоэтапная сборка (Multi-stage build):
  - `Dockerfile.backend`: Стадия сборки `builder` (тяжелый `golang:alpine`, компиляция статических бинарников с флагами `-trimpath -ldflags="-s -w"`) полностью отделена от финального runtime-образа на базе чистого `alpine:3.20`.
  - `web/Dockerfile`: Стадия компиляции Node.js/Vite полностью отделена от итогового легковесного Nginx-контейнера (`nginx:alpine-slim`).
  - Полученные образы иммутабельны.

### VI. Процессы (Processes)
> *Выполняйте приложение как один или несколько процессов без сохранения состояния.*
- **Реализация:** Backend-сервис является абсолютно **Stateless**. Вся персистентная информация сохраняется исключительно в PostgreSQL. Локальное состояние (сессии, файлы, кэши в оперативной памяти между HTTP-запросами) не сохраняется. Любой инстанс бэкенда может быть перезапущен или заменен в любой момент времени без потери пользовательских данных.

### VII. Привязка портов (Port Binding)
> *Экспортируйте службы через привязку к портам.*
- **Реализация:** Бэкенд не полагается на запуск внутри стороннего сервера приложений (вроде Apache/Tomcat). Приложение автономно слушает указанный сетевой порт (`:8080` через встроенную библиотеку `net/http`). Доступ веб-клиентов организуется через обратный прокси Nginx на стандартных портах 80 и 3000.

### VIII. Параллелизм (Concurrency)
> *Масштабируйтесь с помощью модели процессов.*
- **Реализация:** Поскольку бэкенд stateless, горизонтальное масштабирование выполняется запуском дополнительных экземпляров контейнера:
  ```bash
  docker compose up -d --scale backend=3
  ```
  Каждый процесс работает независимо, разделяя нагрузку к СУБД через пул соединений.

### IX. Утилизируемость (Disposability)
> *Максимизируйте надежность за счет быстрого запуска и корректного завершения работы.*
- **Реализация:**
  - **Быстрый старт**: скомпилированный бинарник Go стартует менее чем за **15–20 мс**.
  - **Graceful Shutdown**: в `cmd/api/main.go` и `internal/app/app.go` настроен перехват сигналов `SIGINT` и `SIGTERM` через `signal.NotifyContext`. Сервер прекращает прием новых соединений, дожидается завершения активных HTTP-запросов в течение таймаута (`SHUTDOWN_TIMEOUT=5s`), корректно закрывает пул соединений с базой данных `pool.Close()` и завершает работу с кодом 0 без повреждения данных.

### X. Паритет окружений (Dev/Prod Parity)
> *Держите окружения разработки, предрелиза и продакшна максимально похожими.*
- **Реализация:** И в локальном окружении, и в продакшене используется одна и та же СУБД (PostgreSQL 16), одни и те же Dockerfile и конфигурационные параметры. Это предотвращает распространенные проблемы расхождения (типа «на SQLite работало, а на PostgreSQL упало»).

### XI. Журналирование (Logs)
> *Относитесь к логам как к потоку событий.*
- **Реализация:** Приложение не пишет логи в локальные файлы на диске. Логи формируются через структурированный логгер Go `log/slog` и направляются напрямую в стандартный поток вывода (`stdout`). Логи форматируются в виде JSON-событий (или текстовом формате по конфигурации), готовых к автоматическому сбору Docker Daemon, FluentBit, Vector или Promtail.

### XII. Задачи администрирования (Admin Processes)
> *Выполняйте задачи администрирования и управления как разовые процессы.*
- **Реализация:** Миграции базы данных вынесены в отдельную автономную CLI-утилиту `cmd/migrator` и отдельный контейнер `migrator` в `docker-compose.yml`. Мигратор выполняет накат SQL-скриптов, проверяет таблицу `schema_migrations`, подтверждает готовность схемы и завершается с кодом 0 до старта основного бэкенда (`condition: service_completed_successfully`). Миграции не вшиты в жизненный цикл HTTP-сервера, что исключает гонки при горизонтальном масштабировании реплик.

## 7. Руководство по запуску и проверке

### 1. Быстрый запуск всей системы (одна команда)
```bash
docker compose up --build
```
или с использованием `Makefile`:
```bash
make up
```

### 2. Доступ к интерфейсу и сервисам
- **Web UI (Liquid Glass + Sunny Mascot)**: [http://localhost:3000](http://localhost:3000) (или [http://localhost:80](http://localhost:80))
- **Backend API & Healthz**: [http://localhost:8080/healthz](http://localhost:8080/healthz)
- **PostgreSQL**: `localhost:5433` (внешний порт для предотвращения конфликтов с локальным postgres)

### 3. Проверочные команды Makefile
- `make health` — проверка готовности API и базы данных (`/healthz`).
- `make stats` — отображение актуального потребления памяти и ресурсов контейнерами.
- `make logs` — просмотр структурированного потока логов в реальном времени.
- `make test` — запуск полного набора юнит-тестов бэкенда (`100% PASS`).
- `make down` — корректная остановка контейнеров.
