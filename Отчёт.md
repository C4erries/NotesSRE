# Лабораторная работа №2 (SRE): Развёртывание приложения в Kubernetes (Minikube)

---

## 1. Введение и цель работы

Целью данной лабораторной работы является контейнеризация и оркестрация микросервисного веб-приложения **«Note Service»** (Go 1.24, React 19 SPA, PostgreSQL 16 Alpine) в локальной однонодовой инсталляции Kubernetes (**Minikube**).

В ходе работы:
1. Подготовлены и собраны легковесные Docker-образы сервисов (Backend, Frontend, Migrator).
2. Образы загружены в локальный реестр Minikube.
3. Разработаны декларативные манифесты Kubernetes (`k8s/`).
4. Настроена изоляция секретов, конфигураций и персистентного хранилища данных.
5. Реализована схема взаимодействия сервисов через встроенный CoreDNS Kubernetes.
6. Выполнено горизонтальное масштабирование (`kubectl scale`) и подтверждена работоспособность интерфейса.

## 2. Использованные абстракции Kubernetes

Для запуска и обеспечения высокой доступности сервиса были использованы следующие базовые абстракции Kubernetes:

### 1. `Secret` (`postgres-secret`)
- **Назначение**: Безопасное хранение чувствительных данных (пароль учетной записи PostgreSQL `POSTGRES_PASSWORD`, логин `POSTGRES_USER` и имя базы `POSTGRES_DB`).
- **Файл**: `k8s/00-config.yaml`
- **Особенность**: Передается в поды базы данных через `envFrom`, исключая утечку паролей в публичный код и логи.

### 2. `ConfigMap` (`note-service-config`)
- **Назначение**: Централизованное хранение несекретных конфигурационных параметров приложения (порт `HTTP_PORT`, таймауты `SHUTDOWN_TIMEOUT`, строка подключения `DATABASE_URL`).
- **Файл**: `k8s/00-config.yaml`
- **Соответствие 12-Factor App**: Фактор III («Конфигурация в среде выполнения»).

### 3. `PersistentVolumeClaim` (PVC `postgres-pvc`)
- **Назначение**: Запрос на постоянное дисковое хранилище (1 GiB) для каталога данных PostgreSQL (`/var/lib/postgresql/data`).
- **Файл**: `k8s/01-postgres.yaml`
- **Особенность**: Обеспечивает персистентность (сохранность) данных заметок и категорий даже при перезапуске, перемещении или падении пода СУБД.

### 4. `Deployment` (`postgres`, `backend`, `frontend`)
- **Назначение**: Декларативное управление жизненным циклом подов (создание, перезапуск при сбоях, обновление версий, масштабирование).
- **Файлы**: `k8s/01-postgres.yaml`, `k8s/03-backend.yaml`, `k8s/04-frontend.yaml`.
- **Особенности**:
  - `postgres`: 1 реплика со стратегией `Recreate` (предотвращает конфликт одновременного монтирования тома PVC несколькими подами).
  - `backend`: 2 реплики по умолчанию (масштабируется до 4+), настроены проверки жизнеспособности:
    - `livenessProbe` (`httpGet /healthz:8080`) — перезапускает зависший под.
    - `readinessProbe` (`httpGet /healthz:8080`) — исключает под из балансировки, если база недоступна.
  - `frontend`: 2 реплики Nginx + React SPA с проверками `livenessProbe` и `readinessProbe` по корню `/`.

### 5. `Job` (`note-service-migrator`)
- **Назначение**: Одноразовый запуск административной задачи — накат SQL-миграций структуры таблиц до начала обслуживания пользовательских запросов.
- **Файл**: `k8s/02-migrator-job.yaml`
- **Соответствие 12-Factor App**: Фактор XII («Задачи администрирования как разовые процессы»).
- **Особенность**: Автоматически завершается со статусом `Completed` после наката миграций. `backoffLimit: 10` и встроенный exponential backoff в Go гарантируют надежное ожидание старта PostgreSQL.

### 6. `Service` (`postgres`, `backend`, `frontend`)
- **Назначение**: Сетевая абстракция для обнаружения сервисов (Service Discovery) и балансировки нагрузки между подами.
- **Типы сервисов**:
  - `ClusterIP` (`postgres:5432`): Доступен только внутри кластера.
  - `ClusterIP` (`backend:8080`): Доступен внутри кластера для проксирования запросов из фронтенда.
  - `NodePort` (`frontend:80` -> NodePort `30080`): Публичный эндпоинт для доступа к приложению из браузера хост-машины через `minikube service frontend` или `http://<minikube-ip>:30080`.

## 3. Схема взаимодействия сервисов приложения

Взаимодействие компонентов внутри Kubernetes опирается на встроенный DNS-сервер (**CoreDNS**) и виртуальную маршрутизацию `kube-proxy`:

1. **Запрос пользователя к Frontend**:
   - Пользователь открывает веб-интерфейс в браузере по адресу NodePort-сервиса (или через команду `minikube service frontend`).
   - Запрос попадает на один из подов `frontend` (Nginx). Nginx отдаёт клиенту скомпилированную React SPA (HTML/JS/CSS, Liquid Glass дизайн с маскотом Sunny).

2. **Проксирование API-запросов к Backend**:
   - Клиентский React SPA отправляет REST-запросы по пути `/api/v1/notes` или `/api/v1/categories`.
   - Внутри пода `frontend` конфигурация `nginx.conf` перенаправляет запросы:
     ```nginx
     location /api/ {
         proxy_pass http://backend:8080/api/;
     }
     ```
   - Имя хоста `backend` автоматически разрешается CoreDNS кластера в виртуальный IP-адрес сервиса `backend` (`ClusterIP`), а K8s балансирует нагрузку по алгоритму round-robin между работающими репликами бэкенда (`backend-xxx-1`, `backend-xxx-2` и т.д.).

3. **Взаимодействие Backend с PostgreSQL**:
   - Бэкенд Go читает переменную `DATABASE_URL` из `ConfigMap`:
     `postgres://postgres:postgrespassword@postgres:5432/notes?sslmode=disable`
   - Имя хоста `postgres` разрешается в `ClusterIP` сервиса СУБД.
   - Бэкенд через пул соединений `pgxpool` выполняет транзакционные запросы к таблицам `categories` и `notes`.

4. **Схема первичной инициализации схемы (Migrator)**:
   - При применении манифестов запускается `Job` `note-service-migrator`.
   - Под мигратора обращается к `postgres:5432`, накатывает SQL-скрипты из встроенной `embed.FS` файловой системы (`000001_init_schema.up.sql`), фиксирует версию в `schema_migrations` и завершает работу (`Completed`).

## 4. Демонстрация команд и масштабирования

### 1. Применение манифестов
```bash
kubectl apply -f k8s/
```
Результат:
```
secret/postgres-secret created
configmap/note-service-config created
persistentvolumeclaim/postgres-pvc created
deployment.apps/postgres created
service/postgres created
job.batch/note-service-migrator created
deployment.apps/backend created
service/backend created
deployment.apps/frontend created
service/frontend created
```

### 2. Проверка состояния подов и сервисов
```bash
kubectl get pods -o wide
```
Все поды успешно переходят в состояние `Running`, а мигратор — в `Completed`:
- `postgres-xxx` (1/1 Running)
- `note-service-migrator-xxx` (0/1 Completed)
- `backend-xxx` (1/1 Running, 2 реплики)
- `frontend-xxx` (1/1 Running, 2 реплики)

### 3. Горизонтальное масштабирование (Scaling)
```bash
kubectl scale deployment backend --replicas=4
```
Kubernetes мгновенно планирует и запускает 2 дополнительных пода бэкенда. Благодаря статусу **Stateless** (Фактор VI) все 4 пода параллельно обрабатывают пользовательские запросы.

### 4. Доступ к пользовательскому интерфейсу
```bash
minikube service frontend
```
Открывает браузер с работающим веб-приложением в стиле Liquid Glass, позволяя создавать, закреплять и удалять заметки и категории в реальном кластере Kubernetes.
