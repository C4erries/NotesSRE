# Спецификация проекта: Note Service (SRE Lab 1)

## 1. Цель и контекст
Создание легковесного, отказоустойчивого веб-приложения для ведения заметок, разработанного по методологии **12-Factor App**, с расчетом на последующие SRE-лабораторные (балансировка нагрузки, мониторинг, CI/CD, k8s).

---

## 2. Стек технологий

* **Backend:**
  * Язык: **Go (1.22+)** (используем встроенный улучшенный роутинг `net/http`).
  * Архитектура: **DDD (Domain-Driven Design) / Clean Architecture**.
  * Контракт: **OpenAPI 3.0 (`openapi.yaml`)**.
  * Кодогенерация: **`oapi-codegen`** (генерация DTO-моделей и `StrictServerInterface` для `net/http`).
  * СУБД драйвер: **`pgx/v5` (`pgxpool`)** с использованием чистого SQL (без ORM).
  * Логирование: стандартный **`log/slog`** (структурированный JSON/текст в `stdout`).
* **Frontend:**
  * Стек: **React + Vite** (TypeScript или JavaScript).
  * Раздача в проде/docker: **Nginx Alpine** (минимальный вес ~25 МБ).
  * Взаимодействие: **HTTP/REST (Fetch/Axios)** по контракту OpenAPI.
* **База данных:**
  * **PostgreSQL (15+)**.
* **Инфраструктура и локальный запуск:**
  * **Docker** (Multi-stage сборка для Backend и Frontend).
  * **Docker Compose** (подъем всего окружения одной командой: `db`, `migrator`, `backend`, `frontend`).

---

## 3. Доменная модель (DDD)

### Сущность 1: `Category` (Категория заметок)
* `id` (`UUID` / `string`) — первичный ключ.
* `title` (`string`) — название (например: "Work", "Personal").
* `color` (`string`) — HEX-код цвета для фронтенда (`#FF5733`).
* `created_at` (`time.Time`).

### Сущность 2: `Note` (Заметка)
* `id` (`UUID` / `string`) — первичный ключ.
* `category_id` (`UUID`, nullable / optional) — привязка к категории (FK с `ON DELETE SET NULL` или `CASCADE`).
* `title` (`string`) — заголовок заметки.
* `content` (`string`) — тело заметки (поддержка Markdown).
* `is_pinned` (`bool`) — флаг закрепления наверху списка.
* `created_at` (`time.Time`).
* `updated_at` (`time.Time`).

### CRUD Операции (REST API):
* **Категории:**
  * `POST /api/v1/categories` — создать
  * `GET /api/v1/categories` — список
  * `DELETE /api/v1/categories/{id}` — удалить
* **Заметки:**
  * `POST /api/v1/notes` — создать
  * `GET /api/v1/notes` — список (с фильтром `?category_id=...`)
  * `GET /api/v1/notes/{id}` — получить одну заметку
  * `PUT /api/v1/notes/{id}` — обновить
  * `DELETE /api/v1/notes/{id}` — удалить
* **Служебные (для SRE):**
  * `GET /healthz` — Liveness/Readiness probe (проверка доступности процесса и пинг PostgreSQL).

## 5. Чек-лист соответствия 12 Факторам (для `Отчёт.md`)

1. **I. Кодовая база (Codebase):** Один репозиторий, общий для фронтенда и бэкенда.
2. **II. Зависимости (Dependencies):** Изоляция через `go.mod` (Go) и `package.json` (Node/React). Сборка в изолированных Docker-контейнерах.
3. **III. Конфигурация (Config):** Порты, DSN к Postgres, уровни логов — только через `os.Getenv` / ENV-переменные.
4. **IV. Сторонние службы (Backing services):** PostgreSQL — подключаемый сетевой ресурс (URL).
5. **V. Сборка, релиз, выполнение (Build, release, run):** Multi-stage Dockerfile (этап сборки бинарника отделен от итогового минимального runtime-образа).
6. **VI. Процессы (Processes):** Бэкенд строго stateless. Никакого хранения состояния в ОЗУ между запросами.
7. **VII. Привязка портов (Port binding):** Бэкенд экспортирует `net/http` сервер на порту `${HTTP_PORT}` (по умолчанию `8080`).
8. **VIII. Параллелизм (Concurrency):** Горизонтальное масштабирование запуска нескольких экземпляров бэкенда без конфликтов.
9. **IX. Утилизируемость (Disposability):** Быстрый старт (< 100 мс) и корректный Graceful Shutdown (перехват `SIGINT`/`SIGTERM`, ожидание завершения текущих HTTP-запросов и закрытие пула `pgx`).
10. **X. Паритет окружений (Dev/prod parity):** Одинаковый Postgres 15+ и контейнеры в Dev и Prod.
11. **XI. Журналирование (Logs):** Поток логов через `slog` только в `stdout`. Никаких локальных лог-файлов.
12. **XII. Задачи администрирования (Admin processes):** Миграции БД запускаются как отдельный шаг (`cmd/migrator` или контейнер мигратора), а не внутри основного HTTP-сервера.

# Техническое задание (ТЗ): Сервис заметок («Note Service»)

## 1. Функциональные требования (FT — Functional Requirements)

### FT-1. Управление категориями заметок (CRUD Categories)
* **FT-1.1 (Create):** Создание новой категории с указанием названия (`title`) и HEX-кода цвета (`color`).
* **FT-1.2 (Read):** Получение полного списка существующих категорий.
* **FT-1.3 (Delete):** Удаление категории по её идентификатору (`id`). При удалении категории связанные заметки не удаляются, а получают значение `category_id = NULL` (или удаляются каскадно согласно конфигурации схемы).

### FT-2. Управление заметками (CRUD Notes)
* **FT-2.1 (Create):** Создание новой заметки с указанием заголовка (`title`), текста (`content`), флага закрепления (`is_pinned`) и опционального `category_id`.
* **FT-2.2 (Read List):** Получение списка заметок с возможностью опциональной фильтрации по `category_id`. Сортировка: сначала закрепленные (`is_pinned = true`), затем по дате обновления (`updated_at DESC`).
* **FT-2.3 (Read One):** Получение одной заметки по её уникальному идентификатору (`id`).
* **FT-2.4 (Update):** Полное или частичное обновление заголовка, содержимого, признака `is_pinned` и/или категории заметки. Автоматическое обновление метки `updated_at`.
* **FT-2.5 (Delete):** Удаление заметки по её идентификатору (`id`).

### FT-3. Пользовательский интерфейс (Frontend UI)
* **FT-3.1:** Отображение списка категорий и списка заметок.
* **FT-3.2:** Формы/модальные окна для создания, редактирования и удаления заметок.
* **FT-3.3:** Визуальная фильтрация заметок по выбранной категории.
* **FT-3.4:** Быстрый переключатель признака «закреплена» (`is_pinned`) прямо из карточки заметки.

### FT-4. Служебные интерфейсы (Healthcheck & Readiness)
* **FT-4.1:** Предоставление эндпоинта `GET /healthz`.
* **FT-4.2:** Эндпоинт должен выполнять ping-запрос к СУБД PostgreSQL и возвращать HTTP 200 OK при доступности БД и HTTP 503 Service Unavailable при сбое подключения.

### FT-5. Управление структурой данных (Миграции)
* **FT-5.1:** Автоматизированное создание и обновление таблиц (`categories`, `notes`), внешних ключей и индексов через DDL-скрипты без ручных SQL-запросов в консоли БД.

## 2. Нефункциональные требования (NFT — Non-Functional Requirements)

### NFT-1. Соответствие методологии 12-Factor App
* **NFT-1.1 (I. Codebase):** Единый репозиторий, содержащий бэкенд, фронтенд, миграции и инфраструктурный код.
* **NFT-1.2 (II. Dependencies):** Явная декларация и изоляция зависимостей (файлы `go.mod`, `package.json`, сборка внутри изолированных контейнеров).
* **NFT-1.3 (III. Config):** Конфигурация параметров работы (порт, креды БД, уровень логирования) считывается исключительно из переменных окружения (ENV). Хранение паролей и параметров среды в коде запрещено.
* **NFT-1.4 (IV. Backing services):** СУБД PostgreSQL воспринимается как подключаемый сетевой ресурс через DSN-строку (`DATABASE_URL`).
* **NFT-1.5 (V. Build, release, run):** Разделение фаз на уровне Multi-stage Dockerfile: компиляция бинарника в сборочном образе, запуск — в минимальном runtime-образе.
* **NFT-1.6 (VI. Processes):** Экземпляр бэкенда строго **stateless** — не сохраняет состояние между HTTP-запросами в оперативной памяти или на локальном диске.
* **NFT-1.7 (VII. Port binding):** Бэкенд самостоятельно привязывается к указанному порту (`${HTTP_PORT}`) и слушает входящие HTTP-соединения.
* **NFT-1.8 (VIII. Concurrency):** Масштабирование сервиса обеспечивается запуском нескольких параллельных копий процессов/контейнеров без конкурентных блокировок на уровне приложения.
* **NFT-1.9 (IX. Disposability):** Время холодного старта экземпляра бэкенда не должно превышать 1 секунды. Корректная обработка сигналов завершения (`SIGINT`, `SIGTERM` / Graceful Shutdown) с завершением активных HTTP-запросов и закрытием пула соединений.
* **NFT-1.10 (X. Dev/prod parity):** Одинаковый стек и версии (PostgreSQL 15+) во всех окружениях через Docker Compose.
* **NFT-1.11 (XI. Logs):** Вывод структурированных логов приложения (формат JSON или Key-Value через `slog`) исключительно в стандартный поток вывода (`stdout`). Локальные файлы логов не создаются.
* **NFT-1.12 (XII. Admin processes):** Миграции схемы данных запускаются как отдельный однократный процесс (утилита `migrator`), независимый от жизненного цикла веб-сервера.

### NFT-2. Ресурсоёмкость (Resource Efficiency)
* **NFT-2.1:** Потребление RAM бэкендом в состоянии покоя — не более **30–50 МБ**.
* **NFT-2.2:** Итоговый размер Docker-образа бэкенда — не более **30 МБ** (на базе `alpine` или `scratch`).
* **NFT-2.3:** Итоговый размер Docker-образа фронтенда — не более **30 МБ** (на базе `nginx:alpine`).

### NFT-3. Протокол взаимодействия и контракт
* **NFT-3.1:** Сетевое взаимодействие осуществляется по протоколу **HTTP/1.1 REST**.
* **NFT-3.2:** Формат передачи данных: `application/json`.
* **NFT-3.3 (Contract-First):** Схема API фиксируется в спецификации **OpenAPI 3.0**. Все DTO и сигнатуры хэндлеров на стороне Go генерируются утилитой `oapi-codegen`.

## 3. Ограничения (Constraints)

### C-1. Технологические ограничения
* **Язык бэкенда:** Go (версия 1.22+).
* **СУБД:** PostgreSQL (версия 15+). Использование других СУБД (SQLite, MySQL, MongoDB) запрещено условием курса.
* **Библиотеки доступа к данным:** Использование ORM (Gorm, Ent и др.) **запрещено**; разрешены драйвер `pgx/v5`, пул соединений `pgxpool` и чистый SQL.
* **HTTP-сервер:** Стандартная библиотека `net/http` (без сторонних тяжелых фреймворков вроде Gin/Fiber, совместимо с `oapi-codegen`).
* **Фронтенд:** React SPA (Vite).
* **Запрет протоколов:** Запрещено использовать gRPC и WebSockets для базовых CRUD-операций (во избежание проблем в последующих лабораторных по балансировке).

### C-2. Архитектурные ограничения
* Архитектура бэкенда должна строго следовать слоистой структуре **DDD / Clean Architecture**:
  * `domain`: чистые сущности и интерфейсы репозиториев (0 внешних зависимостей).
  * `application`: сценарии использования (Use Cases / Services).
  * `infrastructure`: реализация репозиториев (`pgx`), HTTP-хэндлеры (`oapi-codegen` + `net/http`).

### C-3. Инфраструктурные ограничения
* Все компоненты системы (`frontend`, `backend`, `database`, `migrator`) должны запускаться одной командой:
  ```bash
  docker compose up --build
  ```
* Запрещено требовать ручной предустановки зависимостей (Go, Node.js, PostgreSQL) на хост-машине проверяющего — всё изолировано внутри контейнеров.

### C-4. Требования к артефактам сдачи
* Исходный код упаковывается в ZIP-архив.
* В корне архива обязателен файл **`Отчёт.md`**, включающий:
  1. Описание доменной области.
  2. Стек реализации.
  3. Основные сущности и схемы таблиц.
  4. Попунктную аргументацию соответствия всем 12 факторам методологии.
